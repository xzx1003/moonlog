# 性能分解与 SHA-256 优化

`run.py` 对固定种子 20261029 的约 100 MiB 档高错误密度文本和 JSON Lines 分别运行两遍，预热一次、正式五次，交替模式顺序。各模式包含相同逐行读取与 UTF-8 解码：

- `read`：只读取与计行。
- `digest`：读取与原始字节 SHA-256。
- `parse`：读取与解析，计数有效时间以消费解析结果。
- `aggregate`：读取、解析、两遍均聚合，最后 finish。
- `full`：原对照适配器，第一遍分析、第二遍解析、两遍摘要、输出 JSON。

这是消融对照，不是内部函数计时。aggregate 两遍都聚合，而 full 只有首遍聚合；不能把各项相加或以 aggregate-full 推算纯阶段开销。暖缓存，未隔离后台负载或控制温度；单机前后结果不能概括所有平台。

优化仅让每个 SHA-256 实例复用 64 个 UInt32 的调度数组，并共享只读轮常量。仍使用纯 MoonBit SHA-256，不降低摘要强度，不跳过任何扫描。`hex()` 的快照单独分配工作区，不改变增量状态。文末另记录按块摘要改造的交错测量；它与本节是两轮独立改动，不能把两轮数字相加。

```bash
moon build benchmarks/compare --target native --release
python3 benchmarks/profile/run.py --binary "$PWD/_build/native/release/build/benchmarks/compare/compare.exe" --output /tmp/profile.json
```

保存结果见 `before.json` / `after.json`。before 是保留的优化前可执行文件；其环境与二进制哈希由测量后补充，计时数据未改动。指标包括逐次 wall、CPU、RSS，完整模式不包含生产 CLI 的上下文和报告排版。

## 本机结果

| 格式 | 模式 | 优化前秒 | 优化后秒 | 耗时变化 |
|---|---|---:|---:|---:|
| text | read | 0.312 | 0.267 | -14.4% |
| text | digest | 1.130 | 1.113 | -1.5% |
| text | parse | 0.574 | 0.506 | -11.8% |
| text | aggregate | 0.824 | 0.810 | -1.7% |
| text | full | 1.449 | 1.426 | -1.6% |
| jsonl | read | 0.322 | 0.305 | -5.2% |
| jsonl | digest | 1.290 | 1.296 | +0.5% |
| jsonl | parse | 0.940 | 0.871 | -7.4% |
| jsonl | aggregate | 1.182 | 1.130 | -4.4% |
| jsonl | full | 2.111 | 1.939 | -8.1% |

这些结果没有置信区间，且 read/parse 对照也有明显波动；不能把全部差值归因于摘要缓冲复用，更不能宣称稳定加速。优化前测量期间做过工具链编译和测试，存在后台负载干扰；交错确认见下节。旧 Go 对照结果未被替换。

## 交错确认

`interleave.py` 把保留的 before 二进制（`/tmp/moonlog-profile-before`，SHA-256 `4753888f…`，与 `before.json` 记录一致）与当前构建（`b485a8a9…`，与 `after.json` 记录一致）按轮交替运行，每模式预热 1 次、正式 5 次，结果存 `interleave.json`；`abab-probe.json` 是更严格的逐对 ABAB 复测（每组 20 对，CPU 秒）。before 来源已核对：从 git 基线 `digest.mbt` 独立重建的对照与保留二进制在五种模式下输出完全一致（构建路径不同导致二进制哈希不同）。

运行期间系统负载约 27–33，不是空闲环境，以下数字只作方向性参考：

| 格式 | 模式 | interleave 中位变化 | ABAB 复测 |
|---|---|---:|---:|
| text | read | -9.6% | -12.0% |
| text | digest | +0.2% | -0.1% |
| text | parse | -6.5% | — |
| text | aggregate | -6.9% | — |
| text | full | -0.7% | — |
| jsonl | read | -10.8% | -11.1% |
| jsonl | digest | -2.6% | -0.8% |
| jsonl | parse | -2.1% | — |
| jsonl | aggregate | -4.7% | — |
| jsonl | full | -1.9% | — |

read/parse 在两个二进制里的代码完全相同，却仍出现约 -9% 至 -12% 的系统差，说明存在构建层面的连带影响（闭包捕获或指令布局等）；该差值就是本次测量的归因底线。针对调度工作区复用的 digest 模式变化为 -0.1% 至 -2.6%，落在底线以内，与噪声无法区分。结论：该优化保证正确性并减少每块调度数组分配，但没有可稳定测量的加速；不宣称稳定加速，也不据此与 Go 比较（Go 对照见 `benchmarks/compare/`，其吞吐量仍明显更高）。

## 按块摘要

`bulk.py` 比较保留的 `/tmp/moonlog-before-bulk`（已复用调度数组、仍逐字节回调，SHA-256 `b485a8a9…`）与当前构建 `_build/native/release/build/benchmarks/compare/compare.exe`（SHA-256 `af1f9c2b…`）。默认 100 MiB 档、预热 1 次、正式 5 次；每轮交替模式顺序（`read`/`digest`/`full` 与反向）和二进制先后。测量包含进程启动、两遍读取、解析/聚合、SHA-256 与输出 JSON；输入生成和输出比较不计时。

每次运行、每种模式都先断言两版本 stdout 完全相等，再计入样本。`digest` 模式额外独立核对：行数为输入行数的两倍（两遍都计行），摘要等于把输入文件顺序读两遍的 SHA-256；`full` 模式核对 JSON 中的输入 SHA-256、总行数和 ERROR 数。结果记录 `load_start` / `load_end`、输入字节数/行数/错误数/SHA-256、二进制 SHA-256 及逐次 wall/user/system/RSS。

```bash
python3 benchmarks/profile/bulk.py --before /tmp/moonlog-before-bulk --after "$PWD/_build/native/release/build/benchmarks/compare/compare.exe" --size 100 --output /tmp/bulk-100.json
```

解读限制：

- `read` 模式也改变了：`observe` 改为默认 `None` 后不再逐字节调用空闭包。因此 read 的变化是预期结果，不能当作完全同码的噪声对照。
- `digest` / `full` 的变化同时包含“去掉空的逐字节回调”和“按块填充 SHA-256”，不能拆成纯 SHA-256 加速。
- 只覆盖受限计算契约，不含生产 CLI 的上下文提取、脱敏、Markdown 报告和完整参数处理；没有重跑 Go 对照或完整 CLI 基准。

### 历史初测（10 MiB）

`bulk.json` 是 10 MiB 档、5 次正式运行的初测，保留不动：load_start 三值（1/5/15 分钟平均）为 32.6–35.5，未记录 load_end；二进制同上。text 的 read/digest/full 中位耗时分别变化 −36.9% / −16.0% / −8.2%，jsonl 为 −36.7% / −14.3% / −6.8%。样本量小，只作方向性记录。

### 100 MiB 档

运行期间负载非空闲：load_start `[28.65, 27.58, 28.32]`，load_end `[15.47, 23.86, 26.86]`（均为 1/5/15 分钟平均）。输入摘要 text `e42dcc26e9638874107cf303bdf69b3c8e43edf67d756d9d5485006e5b90cf3f`，jsonl `c8971ba1d905f9304538639ff38218061547ea07e73c18ad9c40c9d5c0a8c325`。

| 格式 | 输入 | 行数 / 错误 | 模式 | before 秒 | after 秒 | 变化 | after MiB/s |
|---|---|---:|---|---:|---:|---:|---:|
| text | 89,104,890 B | 656,000 / 131,200 | read | 0.2651 | 0.1462 | −44.8% | 581.2 |
| text | 89,104,890 B | 656,000 / 131,200 | digest | 1.1347 | 0.9272 | −18.3% | 91.6 |
| text | 89,104,890 B | 656,000 / 131,200 | full | 1.4416 | 1.3341 | −7.5% | 63.7 |
| jsonl | 105,504,890 B | 656,000 / 131,200 | read | 0.2911 | 0.1646 | −43.4% | 611.2 |
| jsonl | 105,504,890 B | 656,000 / 131,200 | digest | 1.2797 | 1.0894 | −14.9% | 92.4 |
| jsonl | 105,504,890 B | 656,000 / 131,200 | full | 1.9336 | 1.7753 | −8.2% | 56.7 |

read 的约 −43% 至 −45% 与移除空回调相符，但不与 digest/full 的收益相加。digest 降低约 15%–18%，full 降低约 7.5%–8.2%；full 的绝对收益较小，因为同一轮还包含解析、聚合与输出。两遍扫描和 SHA-256 均未删减。各模式进程峰值 RSS 为 2.00–2.44 MiB，按块回调没有带来可测的内存增长。上述为 5 次正式运行的中位数，无置信区间；暖缓存、未控制温度，结果只代表本机该负载下的受限契约。原始样本保存在 [`bulk-100.json`](bulk-100.json)。
